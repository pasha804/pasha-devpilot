SECTION 2: THE CORE PROBLEM VS. PASHA DEVPILOT SOLUTION
====================================================================================================

2.1 The Crisis of First-Generation AI Assistants (Copilots & Chatbots)
Modern software development has seen an explosion of generative AI code models. However, when deployed
in production environments, software engineering teams experience four major failure modes:

  A. SINGLE-FILE BLINDNESS & LACK OF REPOSITORY CONTEXT:
     Existing tools operate within the narrow context of an active editor window or a short conversation
     buffer. They lack whole-project awareness, failing to comprehend cross-module imports, database
     schemas, or configuration constraints. A fix applied in one file frequently breaks downstream
     consumers across five other files.

  B. HALLUCINATED, UNTESTED CODE OUTPUTS:
     Standard LLMs produce code based on probabilistic token prediction. They have no innate capacity
     to execute code, verify syntax, or run test runners. Developers find themselves spending more time
     debugging the AI's subtle logical flaws and syntax hallucinations than if they had written the
     code manually.

  C. ABSENCE OF SAFETY BOUNDARIES & DANGEROUS EXECUTION RISKS:
     Autonomous agents with unconstrained shell access pose severe infrastructure threats. Without
     strict sandboxing, an agent can accidentally execute destructive commands such as 'rm -rf',
     force-push over protected production branches, or trigger path-traversal escapes that corrupt the
     underlying host system.

  D. INSECURE CREDENTIAL MANAGEMENT:
     Many developer tools demand that users generate and copy-paste long-lived GitHub Personal Access
     Tokens (PATs) with sweeping permissions. These tokens frequently leak through browser local storage,
     prompt histories, or unmasked server logs.

SECTION 5: THE 7-STATE FINITE STATE MACHINE (FSM) ORCHESTRATION ENGINE
====================================================================================================

The entire lifecycle of every engineering task is governed by a formal, deterministic 7-State Finite
State Machine implemented in `packages/agent_core/orchestrator/orchestrator.py`. Unlike ad-hoc prompt
chains, this FSM enforces rigid entry conditions, execution boundaries, and human checkpoints.

```
[1. UNDERSTANDING] ➔ [2. INVESTIGATING] ➔ [3. PLANNING]
                                                 |
                                                 v
[5. IMPLEMENTING] 🠔 [4. WAITING_FOR_APPROVAL (HUMAN GATE)]
       |
       v
[6. VERIFYING] ──(Tests Fail, Retries < 3)──➔ (Self-Healing Loop)
       |
       v (Tests Green)
[7. REVIEWING / READY_TO_SHIP] ➔ [GitHub PR Created]
```

5.1 Deep Dive into Each State

----------------------------------------------------------------------------------------------------
STATE 1: UNDERSTANDING
----------------------------------------------------------------------------------------------------
  - Purpose: Construct a complete mental map of the target codebase before touching anything.
  - Actions:
      1. Clones the selected GitHub repository into an ephemeral sandbox directory: `temp_sandboxes/{task_id}/`.
      2. Scans project configuration manifests to auto-detect build tools (`pyproject.toml`, `package.json`,
         `Cargo.toml`, `go.mod`).
      3. Recursively parses all source code files through the AST parser (`apps/api/services/ast_indexer.py`).
      4. Extracts all declared classes, methods, functions, docstrings, imports, and dependencies.
      5. Builds an in-memory symbol graph identifying which modules depend on each other.
  - Exit Condition: Symbol graph is fully constructed; moves automatically to `INVESTIGATING`.

----------------------------------------------------------------------------------------------------
STATE 2: INVESTIGATING
----------------------------------------------------------------------------------------------------
  - Purpose: Diagnose the defect by running baseline tests and capturing raw system telemetry.
  - Actions:
      1. Executes the project's existing test harness (`pytest tests/ -v` or `npm test`) inside the sandbox.
      2. Captures exit code, stdout, and failure tracebacks.
      3. Queries **IBM Bob** (`bob-code-plus`) with the prompt, the failure tracebacks, and the AST symbol map.
      4. Generates an evidence-backed engineering diagnostic report identifying:
         - The exact root-cause file and line numbers.
         - The underlying logical failure (e.g., inverted comparison operator, arithmetic error).
         - The blast radius and potential side effects on other modules.
  - Exit Condition: Diagnostic report is saved to task record; moves to `PLANNING`.

----------------------------------------------------------------------------------------------------
STATE 3: PLANNING
----------------------------------------------------------------------------------------------------
  - Purpose: Synthesize a structured, step-by-step implementation plan.
  - Actions:
      1. IBM Bob synthesizes an ordered list of implementation steps.
      2. For each step, it specifies:
         - Target file path.
         - Action type (modify, create, delete).
         - Description of the required logical change.
         - Regression risk evaluation.
      3. Packages the plan into a structured JSON payload.
  - Exit Condition: Plan is persisted; transitions immediately to `WAITING_FOR_APPROVAL`.

----------------------------------------------------------------------------------------------------
STATE 4: WAITING_FOR_APPROVAL (THE HUMAN-IN-THE-LOOP GATE)
----------------------------------------------------------------------------------------------------
  - Purpose: Ensure absolute developer sovereignty over the codebase.
  - Rules:
      1. THE PIPELINE COMPLETELY PAUSES EXECUTION.
      2. Zero write operations, file modifications, or Git commits are permitted in this state.
      3. Emits an event to the frontend UI, opening the interactive **Approval Modal**.
      4. The engineer reviews the proposed plan, changes, and risk analysis.
      5. User Choices:
         - **APPROVE**: Calls `POST /api/v1/tasks/{id}/approve` -> Transitions to `IMPLEMENTING`.
         - **REVISE** : Submits user feedback -> Transitions back to `PLANNING` to regenerate plan.
         - **REJECT** : Cancels task and cleans up the sandbox workspace.
  - Exit Condition: Explicit user approval received via authenticated API call.

----------------------------------------------------------------------------------------------------
STATE 5: IMPLEMENTING
----------------------------------------------------------------------------------------------------
  - Purpose: Apply surgical, high-precision code modifications in the sandbox.
  - Actions:
      1. IBM Bob generates unified diff chunks targeting the approved files.
      2. Diffs use standard unified diff hunk syntax (`@@ -start,len +start,len @@`).
      3. The sandbox patch engine applies the hunks atomically.
      4. Syntax validation: Verifies that the modified file still parses cleanly into an AST without
         syntax errors.
  - Exit Condition: All file diffs applied cleanly; moves automatically to `VERIFYING`.

----------------------------------------------------------------------------------------------------
STATE 6: VERIFYING (TRUTHFUL BOUNDED SELF-HEALING)
----------------------------------------------------------------------------------------------------
  - Purpose: Prove that the code changes actually work by running real unit tests.
  - Actions:
      1. Executes the test runner inside the sandbox (`pytest tests/ -v`).
      2. Streams live test logs to the frontend terminal visualizer.
      3. Branch A: ALL TESTS PASS (Exit code 0):
         - Verification confirmed green!
         - Transitions immediately to `REVIEWING`.
      4. Branch B: TESTS FAIL (Exit code != 0):
         - Increments retry counter (`attempt_count += 1`).
         - If `attempt_count <= 3`:
           * Captures the new failure traceback.
           * Feeds the traceback back into IBM Bob with prompt:
             "Your previous patch resulted in test failure: [TRACEBACK]. Synthesize an updated patch."
           * Applies corrected diff in sandbox and re-executes tests.
         - If `attempt_count > 3`:
           * Halts execution and marks task status as `VERIFICATION_FAILED`.
           * Reports the failure truthfully to the user rather than faking success.
  - Exit Condition: Tests pass cleanly (or max retries reached).

----------------------------------------------------------------------------------------------------
STATE 7: REVIEWING / READY_TO_SHIP
----------------------------------------------------------------------------------------------------
  - Purpose: Present the final verified diff to the developer and publish to GitHub.
  - Actions:
      1. Generates complete unified diffs of all modified files.
      2. Loads the diffs into the integrated **Monaco Diff Editor** in the UI.
      3. Displays total additions (+), deletions (-), and modified files.
      4. When the user clicks **"Ship Pull Request"**:
         - Creates a dedicated Git branch: `devpilot/fix-{task_id}`.
         - Commits the modified files with a clear, conventional commit message.
         - Pushes the branch to the remote origin on GitHub.
         - Authors a comprehensive GitHub Pull Request via the GitHub REST API containing:
           * Summary of problem and solution.
           * Step-by-step changelog.
           * Verified test execution output proving all tests pass.
  - Exit Condition: GitHub Pull Request URL generated; task marked as `COMPLETED`.

SECTION 7: RESTRICTED EXECUTION SANDBOX & ZERO-TRUST SECURITY JAIL
====================================================================================================

7.1 Architecture of the Sandbox Jail
The sandbox execution engine is implemented in `apps/api/services/sandbox_service.py`. Its primary
mandate is to protect the host infrastructure from unauthorized modifications, destructive commands,
and credential exfiltration.

7.2 Security Guardrails & Enforcement Layers

  A. STRICT BINARY ALLOWLISTING:
     Arbitrary shell commands are completely rejected. Only approved development and testing binaries
     can execute within the sandbox environment:
       - Python   : `pytest`, `python -m pytest`, `python -m unittest`, `ruff`, `mypy`, `pip list`
       - Node.js  : `npm test`, `npx vitest`, `npx jest`, `npm run build`, `tsc`, `pnpm test`
       - Go / Rust: `go test`, `cargo test`
       - Git (Safe): `git status`, `git diff`, `git log`, `git checkout`, `git add`, `git commit`

  B. DESTRUCTIVE COMMAND DENYLIST:
     Any execution request matching dangerous shell patterns triggers an immediate `SecurityException`
     and halts the task:
       - System Destructive : `rm`, `del`, `format`, `shutdown`, `reboot`, `kill`, `pkill`
       - Pipeline Exploits  : `curl | bash`, `wget | sh`, `powershell -enc`, `eval()`

8.2 Seeded Defect 1: Inverted Token Expiration Math (`src/auth_service.py`)
In `src/auth_service.py`, lines 65–69:
```python
# DEFECTIVE CODE:
now = datetime.now(timezone.utc)
if token.expires_at > now:
    raise TokenExpiredError(f"Token '{token_id}' expired at {token.expires_at}.")
```
  - The Error: The developer mistakenly used `>` instead of `<`. As a consequence:
    * All freshly issued, valid future tokens trigger `TokenExpiredError` and are rejected!
    * Any genuinely expired token from the past mistakenly passes through as valid!
  - Test Impact:
    * `tests/test_auth.py::test_issue_and_verify_valid_token` -> FAILED (TokenExpiredError)
    * `tests/test_auth.py::test_expired_token_rejected` -> FAILED (Did not raise)
    * `tests/test_auth.py::test_missing_scope_raises_error` -> FAILED (Premature expiration)

8.3 Seeded Defect 2: Inverted Discount Arithmetic (`src/billing_service.py`)
In `src/billing_service.py`, lines 54–62:
```python
# DEFECTIVE CODE:
def calculate_invoice_total(self, subtotal: float, discount_percent: float, tax_rate: float = 0.10) -> float:
    discount_amount = subtotal * (discount_percent / 100.0)
    # Bug: Discount is added rather than subtracted!
    discounted_subtotal = subtotal + discount_amount
    total = discounted_subtotal * (1.0 + tax_rate)
    return round(total, 2)
```
  - The Error: Promotional discount amount is added to the subtotal instead of subtracted.
    Customers entitled to a 20% discount on a $100 invoice are charged $132.00 instead of $88.00!
  - Test Impact:
    * `tests/test_billing.py::test_calculate_invoice_with_promotional_discount` -> FAILED
      `AssertionError: Expected total $88.00 after 20% discount, but got $132.0`

13.1 Issue: GitHub OAuth "Redirect URI Mismatch"

              OAuth App settings.

13.2 Issue: Sandbox Reports `AccessDeniedError`
  - Cause   : A script attempted to access a path containing `../` or outside `temp_sandboxes/`.
  - Solution: Inspect the task prompt to ensure file references are relative to the repository root.

13.3 Issue: Verification Fails after 3 Attempts
  - Cause   : The underlying code defect requires architectural changes beyond surgical diff patching.
  - Behavior: DevPilot truthfully reports failure rather than hallucinating success.
  - Remedy  : Review the terminal tracebacks in the UI, revise the prompt with specific guidance, and
              re-launch the task.

13.4 Issue: IBM Bob API Rate Limit Reached
  - Behavior: `ModelRouter` automatically switches to DeepSeek V4 Flash or Groq LLaMA 3.3.
  - Remedy  : Verify your IBM Bob token quota in the IBM Bob console.
